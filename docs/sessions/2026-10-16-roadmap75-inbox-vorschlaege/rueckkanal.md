## 2. Befunde

**[wichtig] F-A — `bannerApplyErrors`-Leiche: veraltete Fehlermeldung erscheint nach „Ignorieren → Wieder anzeigen" erneut.** [advocatus B1, von mir am Code verifiziert.] Pfad: Apply wirft → `bannerApplyErrors.set` (app.js:12837) → Nutzer klickt „Ignorieren" (Handler :12806–12809 löscht die Map NICHT) → Gruppe liegt in Zone 3, Meldung wird dort nicht gezeichnet (:12735–12750 ohne Error-Block) → „Wieder anzeigen" (`clearInboxGroupIgnored` :12627–12636 löscht die Map NICHT) → Gruppe ist wieder offen, `updateGroupBannerUI` zeichnet die ALTE Meldung erneut (:12677–12678). Kein Datenverlust, aber genau die „stiller Schmutz"-Klasse, die #80 abgeschafft hat. Die Implementierung ist treu zu AK9 („gelöscht beim nächsten Apply-Versuch") — das ist eine Lücke im AK9-Design, nicht im Code. **Empfehlung: jetzt beheben (Gate-A2-Lauf 2 oder gezieltes Nachfolge-Commit vor PR)** — Einzeiler `bannerApplyErrors.delete(groupKey)` im Ignorier-Handler und/oder in `clearInboxGroupIgnored`, plus ein kleiner Test. Kein Abnahmehindernis, weil der Patch das freigegebene Briefing korrekt umsetzt; sollte aber nicht unbehoben in den PR.

**[wichtig] F-B — Hängende Suche blockiert alle weiteren Banner-Starts dauerhaft (bis Reload/neue Suche).** (Auftrag-Hinweis b; [advocatus B2], verifiziert.) `searchSeries` hat einen `AbortController` (app.js:3085–3088), aber **keinen Timeout**; Abort erfolgt nur bei neuem Suchlauf. Der Apply-Handler `await`et das Promise (:12833), `groupWorkflowRunning` wird ausschließlich im `finally` (:12844) zurückgesetzt. Hängt `/api/search` (Backend-Thread klemmt, Netzwerkpartition ohne Socket-Close), bleibt die Sperre für alle Banner-Apply-Klicks stehen; Ignorieren/Wiederanzeigen/Liste bleiben nutzbar. Das fehlende Timeout ist vorbestehend, die Sperre (von Alex angenommen) verstärkt die Folge. **Empfehlung: ROADMAP-Folgepunkt** (Timeout um das `await` oder Watchdog-Reset der Sperre). Im Lokalbetrieb (localhost/NAS) unwahrscheinlich; kein Blocker.

**[kosmetisch] F-C — Hinweis (a): Prüfreihenfolge „ignoriert vor angewendet" — Begründung des Briefings stimmt, der Edge-Fall ist sogar unerreichbar.** Verifiziert per grep: `appliedInboxGroups.add` existiert genau einmal, im Banner-Apply-Handler (app.js:12830); Bulk-Weg und Gruppenzeile schreiben das Set NICHT. Banner-Apply setzt nur Gruppen, die zuvor offen (also nicht ignoriert) waren — der Zustand „ignoriert UND angewendet" ist im aktuellen Code nicht herstellbar. Die Briefing-Begründung („durch Semantik erledigt": Zonen 1/2 zeigen nur „nicht angewendet && nicht ignoriert" :12661, „Wieder anzeigen" ist reines `removeItem` :12627–12636) stimmt mit dem Code überein und wäre selbst dann harmlos (Gruppe würde still verschwinden — genau das produktberater-konforme Verhalten). **Dissens dokumentiert:** [produktberater] forderte die „explizite bereits-angewendet-Prüfung" (~5 Zeilen) als „vor dem Merge beheben", basierend auf der Annahme, der Bulk-Weg schreibe `appliedInboxGroups` — diese Annahme ist widerlegt (grep-Beweis oben); sein Nachbesserungspunkt wird daher verworfen.
